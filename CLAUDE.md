## Fluxo de trabalho — branches + PR, main protegida

Desde 2026-07-29, `main` tem branch protection (`enforce_admins: true`, sem bypass nem para admin):

- **Push direto em `main` é bloqueado.** Todo trabalho vai para uma branch, com PR para `main`.
- **Checks obrigatórios antes do merge**: `build` (GitHub Actions — `.github/workflows/ci.yml`, roda lint + build) e `Vercel` (preview deployment do PR precisa ficar verde).
- **Sem revisão humana obrigatória** — decisão consciente, dado que o projeto é mantido por uma pessoa só. Os checks automatizados são o gate.
- `allow_force_pushes: false`, `allow_deletions: false` em `main`.
- Por quê: reversibilidade (cada PR é um ponto de revert limpo) + garantia de que nada quebra o build/deploy antes de entrar em `main`.

Fluxo prático para qualquer mudança a partir daqui:
```bash
git checkout -b nome-da-branch
# ...commits...
git push -u origin nome-da-branch
gh pr create --fill
# esperar checks (build + Vercel) ficarem verdes, então:
gh pr merge --squash  # ou merge normal, conforme preferir
```

## Requisitos de segurança — não-negociáveis

Direto de `docs/projeto-celula.md` §7. Um agente de IA "implementa o que você pede, mas raramente sugere proteções que você não pediu" — por isso ficam explícitos aqui, não implícitos:

1. **RLS obrigatório em toda tabela nova**, sem exceção — mesmo sem "conta de usuário".
2. **Conteúdo editorial é somente leitura para o app.** `pregacoes` e `quebra_gelos` (e qualquer tabela de conteúdo futura) nunca têm policy de insert/update/delete para o role de aplicação (`app_readonly`, desde a migração para Neon — ver "Decisões de arquitetura (Migração Neon)"). Escrita só via `DATABASE_URL_ADMIN` (script local, fora do client/deploy).
3. **Dado efêmero de sessão** (resultado de sorteio, nome digitado numa dinâmica) pode ter escrita livre — não tem valor de permanência, não precisa das mesmas garantias do conteúdo editorial.
4. **Rate limiting nos utilitários** (ex: Vercel Firewall/`@vercel/firewall` ou Upstash + `@upstash/ratelimit`) antes de qualquer utilitário ficar acessível publicamente sem autenticação. Ainda não implementado — utilitários continuam 100% client-side sem chamada de rede (ver Fase 3), então não há superfície de rede a proteger hoje; vira requisito real no dia em que um utilitário ganhar backend.
5. **Sem PII persistida** além da sessão, a não ser que histórico seja explicitamente decidido depois.

Ao adicionar uma tabela nova: habilitar RLS na mesma migração que cria a tabela, nunca depois.

**`API_BASE_URL` hardcoded em `src/lib/api.ts` é pública por design** (URL do domínio Vercel), mesma lógica de antes com a anon key do Supabase: não é segredo, é config pública que vai no bundle do client. O que **nunca** pode ser hardcoded ou ir para o bundle do client é `DATABASE_URL`/`DATABASE_URL_ADMIN` (connection string real do Postgres) — essas só existem em `.env.local` (gitignorado) e nas env vars do projeto Vercel, nunca em código.

## Práticas de desenvolvimento

- **TDD nasce junto com o código.** Utilitários (sorteador, contador) e lógica de renderização de conteúdo nascem com teste, não como algo adicionado depois.
- **Refactoring contínuo é disciplina.** A separação em camadas (conteúdo / utilitários locais / roteamento por feature — ver `docs/projeto-celula.md` §7) exige poda regular, não desenho único.
- **O humano decide o quê, a IA decide o como.** Questionar decisões de arquitetura propostas (ex: recusar over-engineering, state machine complexa quando um caso simples resolve).
- **Modularidade para a V2.** Utilitários da V1 (sorteio single-device) são módulos isolados desde já, pensados para serem *estendidos* com sincronização real-time na V2 — não reescritos. Mecanismo concreto em aberto desde a migração para Neon (ver "Decisões de arquitetura (Migração Neon)").
- **`docs/progresso.md` é a única fonte de verdade de progresso — nunca uma cópia paralela.** Spec/planejamento trazido de fora do repositório (mensagem do Carlos, documento externo) referencia a fase/seção correspondente de `progresso.md` ao ser incorporado, em vez de duplicar status. Decidido em 2026-08-05 depois de desalinhamento real entre uma cópia externa e o repo (Fase 3 já concluída aqui, "não iniciada" na cópia).

## Decisões de arquitetura (Fase 2)

- **Router próprio (`src/router/`), não `react-router-dom`.** O app só precisa de ~4 rotas estáticas; a lib puxava uma cadeia de CVEs do modo framework/RSC (SSR, actions) que este app nunca usa (SPA client-side puro). Antes de adicionar uma lib de roteamento "de verdade" no futuro, reavaliar se ainda faz sentido dado o tamanho real do app.
- **`componente_tema` é um registro por variante, não por tema.** Qualquer variante (`stage`, `diagnostico`, etc.) pode aparecer em qualquer pregação — confirmado no conteúdo real (`stage`, documentado como do Estilo #1/#2, apareceu numa pregação do Igrejar). Um único componente por `variante` em `src/content/ComponenteTemaRenderer.tsx`, cores resolvidas via CSS custom properties do tema ativo. Variante desconhecida não quebra a renderização (retorna `null`, `console.warn` em dev).
- **Tema é escopado por componente (`ThemeScope`), não só por tela.** A casca do app (tab bar) usa Padrão MINC; cada card da Biblioteca aplica o tema da própria série; a tela de Leitura aplica o tema da pregação. CSS vars via `style` inline num wrapper — funciona porque custom properties cascateiam normalmente.
- **Busca da Biblioteca é client-side.** Dataset pequeno (dezenas de registros) — sem Postgres full-text search por enquanto. Reavaliar se o catálogo crescer para centenas de pregações.
- **Datas em português exigem conversão.** `metadados.data` no JSON vem como `"26 de julho de 2026"`; a coluna `pregacoes.data` é `date` nativo do Postgres, que não entende nome de mês em PT-BR. `src/content/parseData.ts` (`parseDataPtBr`/`formatDataPtBr`) é o conversor canônico — usar sempre que inserir conteúdo novo, nunca inserir a string crua na coluna `data`.
- **Tela de Leitura reescrita para "Leitura Contínua" (2026-08-16), substituindo — não coexistindo com — o layout anterior.** Decisão de Carlos ao aprovar o mock: V1 enxuta, mantida por 1 pessoa, sem caso de uso que justifique duas UIs de leitura em paralelo. Mudanças: header sticky (voltar/título/botão "Aa" de escala de fonte, efêmero) + trilha de chips (um por `mapa_pontos[]`) + barra de progresso fina, todas dentro do mesmo `.headerSticky`; nav inferior fixo (anterior/próximo) posicionado acima da tab bar do `AppShell` (`bottom: calc(76px + safe-area)`). O antigo FAB (`useIndiceFab`, aparecia/sumia conforme o índice saía da viewport) foi removido — `src/screens/pregacoes/useLeituraNav.ts` o substitui com `useSecaoAtiva` (um único `IntersectionObserver` com múltiplos degraus de `threshold`, comparando `intersectionRatio` entre todas as seções pra achar a "ativa" — mecanismo diferente do antigo, que só perguntava "o índice ainda está visível?") e `useScrollProgress` (scroll passivo + `requestAnimationFrame`, mesma lição de bateria/WebView já registrada no polling do Artista Impostor — nunca `setInterval`). **Decisão consciente de manter o índice grid existente** (bloco grande entre banner e seções) — a trilha sticky dá contexto contínuo durante a leitura, mas o grid continua útil como visão geral/pulo direto ao compartilhar na célula; não fazia parte do que o mock pedia remover.
- **`componente_tema` variante `analogia` é colapsável por padrão (fechada), em qualquer tema/tela** — decisão de produto junto com a Leitura Contínua, sem campo novo no payload (`ComponenteTemaRenderer.tsx`, `Analogia`). Efeito automático em qualquer consumidor do componente compartilhado, sem precisar tocar em mais nada.
- **Escala de fonte do botão "Aa" via CSS var (`--leitura-escala`) definida no wrapper raiz da Leitura, consumida em `calc()` nos `font-size` de texto de corpo** (`Reading.module.css` e `BlockRenderer.module.css` — parágrafo, versículo, callout, frase-chave, lista). Escopo deliberadamente contido: não toca em labels/badges/chips (UI de navegação) nem nos blocos decorativos de `componente_tema` (analogia, diagnóstico, contraste etc.) — só o texto de leitura corrida. `font-size` em `px` não escala com `font-size` do pai (diferente de `em`/`rem`), por isso a var precisa estar em cada regra via `calc()`, não só declarada uma vez no topo.
- **`conteudo.resumo_curto` (2026-08-19, feedback real sobre pregações longas dificultando leitura de membros "leigos") renderiza como um CTA de destaque na Leitura, que abre `ResumoCurtoOverlay` — tela cheia própria, não modal/dialog.** Reaproveita o padrão de overlay já usado em `Detalhe.tsx` (`position: fixed; inset: 0; z-index: 20`, retorno condicional antes do JSX principal), agora dentro do mesmo `ThemeScope` da Leitura (diferente de `Detalhe.tsx`, que não depende de tema). Campo opcional, sem consumidor obrigatório — pregação sem `resumo_curto` não mostra o botão. Ver `docs/geracao-pregacao.md` para o schema e a distinção de propósito frente a `resumo_final` (recapitulação pós-leitura vs. substituto de leitura pré-seções).
- **`Theme.fonteH1`/`Theme.pesoH1` (`src/themes/types.ts`, 2026-08-24) — par opcional de campos pra um tema querer uma fonte "assinatura" exclusiva do `header h1`, sem ela vazar pro resto do documento.** Motivado pelo Estilo #6 (brush Kalam): a primeira implementação vazou o brush pra vários lugares porque quase todo título no app (índice, `secaoTitulo`, badges, CTAs, callouts) referencia o mesmo `var(--font-display)`/`var(--font-display-weight)` compartilhado — patchear seletor por seletor com override escopado por tema (`[data-tema="..."]`) resolveria os pontos já vistos, mas deixaria a porta aberta pra qualquer título futuro vazar de novo. Resolvido invertendo a relação em vez de listar exceções: `fonteDisplay` do Estilo #6 virou a fonte sóbria (mesma família de `fonteCorpo`), e só `fonteH1` ficou com o Kalam — `ThemeScope.tsx` expõe `--font-h1`/`--font-h1-weight` (fallback pra `fonteDisplay`/`pesoDisplay` quando o tema não define `fonteH1`, então todo tema que não é o #6 se comporta exatamente como antes) e só `.headerTitulo` em `Reading.module.css` referencia essas duas vars — todo o resto do app continua em `var(--font-display)`, agora automaticamente sóbrio pro #6 sem precisar tocar em cada arquivo. Padrão reutilizável — qualquer tema futuro com uma fonte de "capa"/assinatura só pro h1 usa os mesmos dois campos.
- **`--seal`/`--seal-soft` (vermelho de cera do Estilo #6) é estritamente decorativo — nunca cor de fonte (`color`), só borda/fundo.** Correção de Carlos depois de ver o preview real do PR: vermelho saturado sobre o marrom kraft do tema tem contraste ruim pra leitura de texto corrido, não só nos dois pontos do achado de acessibilidade anterior (referência bíblica, badge de série — 2026-08-22). Como não existe (e não vale a pena criar) um token de design system genérico "cor de acento nunca é cor de fonte" pros outros 6 temas — nenhum deles teve o mesmo problema reportado — a correção é local ao Estilo #6: todo `color: var(--accent1)`/`color: var(--accent2)` dentro de CSS compartilhado (`Reading.module.css`, `BlockRenderer.module.css`, `ComponenteTemaRenderer.module.css`, `Keyword.module.css`, `SermonCard.module.css`, `ResumoCurtoOverlay.module.css`) ganhou um override escopado por `[data-tema="estilo-6-uma-vez-salvo"]` trocando pra `--text`/`--muted`; usos como `border-color`/`background` ficaram intocados. Ver `docs/estilos-pregacao.md` § Estilo #6 pra lista completa e a exceção (`.ctaCompleta`, onde o vermelho é fundo do botão, não cor do texto por cima).

## Decisões de arquitetura (Fase 3)

- **`quebra_gelos.tipo='utilitario'` são as 3 ferramentas da aba Utilitários, não uma categoria à parte.** A migração de Fase 1 já tinha 3 valores no CHECK (`instrucional`/`utilitario`/`instrucional_utilitario`), mas nenhum dos 9 itens reais do catálogo de quebra-gelos usa `utilitario` puro — esse valor só serve para as linhas-ferramenta de `/utilitarios`. Unifica os dois módulos numa única tabela, sem tabela nova nem migração.
- **Fluxo de privacidade sequencial compartilhado entre sorteio de atribuição e sorteio de papel** (`docs/spec-privacidade-sorteio.md`, `src/utilitarios/passagemSequencial/`). Os dois widgets diferem só em *o que* é sorteado; o mecanismo de "passar o celular" (setup → passagem revelar/confirmar/próximo por pessoa → gestão do líder com valores ocultos por padrão) é um hook único (`usePassagemSequencial`) consumido por ambos. Decisão de implementação: só o caminho de toque explícito ("Quer rever antes de passar?" → toque), sem timer automático — o spec permite ambos, mas o toque evita introduzir `setTimeout`/`vi.useFakeTimers` numa peça que já tem estado suficiente; timer automático fica como extensão isolada do hook se pedido depois. Natureza explicitamente temporária (V1 single-device, um celular circulando) — não generalizar para além disso quando a V2 (multiplayer via lobby) chegar.
- **`atribuir()` é o único primitivo de distribuição, vive em `src/utilitarios/shuffle.ts`** (não em `sorteioAtribuicao/`, apesar do nome parecido) — embaralha uma lista de valores e distribui 1:1 entre participantes. Sorteio de atribuição passa valores livres digitados pelo usuário; sorteio de papel especial passa "fichas" geradas por `sorteioPapel/papeis.ts` (`gerarFichas`, que expande cada papel configurado em N cópias do seu nome — ex: `{nome:"Cidadão",quantidade:3}` vira 3 fichas `"Cidadão"`). Ambos os widgets convergem no mesmo `atribuir()`; não há lógica de sorteio duplicada entre eles.
- **Sorteio de papel especial suporta múltiplos papéis simultâneos com quantidade explícita** (`docs/spec-privacidade-sorteio.md` § Extensão: papéis múltiplos) — não um único "papel_nome" livre como na primeira versão. Setup exige que a soma das quantidades bata exatamente com o total de participantes antes de liberar "Sortear" (`SetupParticipantes.podeIniciarExtra`); mismatch mostra aviso ("faltam N" / "excesso de N"), nunca sorteia parcialmente. Achado ao revisar o primeiro protótipo funcional — dinâmicas reais (ex: jogo do Detetive) precisam de papéis únicos (1 Detetive) e repetíveis (N Cidadãos) ao mesmo tempo.
- **Sem escrita em banco para resultados de utilitário.** 100% estado local client-side e efêmero — nenhuma tabela de sessão, nenhuma persistência. Pensado para a V2 trocar esse estado local por sincronização real-time entre celulares (lobby multiplayer) — mecanismo concreto ainda em aberto desde a migração para Neon, que não tem um equivalente nativo ao Realtime do Supabase (ver "Decisões de arquitetura (Migração Neon)").
- **`usePassagemSequencial.nomes` persiste em `localStorage` (não banco), `src/utilitarios/passagemSequencial/nomesStorage.ts`** — adicionado em 2026-08-13 por feedback real: mesma célula reabre "Encontre o Líder" e depois "sortear detetive" (widgets diferentes, mesmo hook compartilhado) e tinha que redigitar a lista de nomes toda vez, já que o estado morria ao fechar o widget. Diferente da regra acima (resultados de sorteio continuam 100% efêmeros, sem persistência) — nomes de participantes são só *input de setup*, não resultado, e não é dado sensível (nem PII com valor de permanência: CLAUDE.md item 3 já trata "nome digitado numa dinâmica" como dado de escrita livre). `reiniciar()` também limpa o localStorage (reset explícito = esvaziar de verdade, não só a UI).
- **`UtilitarioInlineRef.papeis` (preset vindo do conteúdo de um quebra-gelo) é valor inicial editável, nunca override fixo.** `SorteioPapel` sempre mostra o `PapeisEditor`, pré-preenchido com o preset quando existe — um preset parcial (ex: só "Detetive × 1", caso comum de jogos com 1 papel especial + resto sem papel) nunca teria como bater a soma com o total de participantes sozinho, já que a contagem só é conhecida em tempo real no momento do sorteio. Corrigido antes de existir consumidor real (Detalhe de quebra-gelo) — testado com "Encontre o Líder" (preset "Detetive × 1"), confirmando que o editor abre pré-preenchido e ainda aceita completar/ajustar.
- **Catálogo de quebra-gelos e catálogo de utilitários usam o mesmo `CatalogCard`**, e o Detalhe de quebra-gelo reaproveita os 3 widgets de `/utilitarios` via overlay local (`useState<UtilitarioInlineRef | null>`) — nenhuma lógica de sorteio/cronômetro duplicada entre os dois módulos. `ComingSoon` (placeholder da Fase 2) removido do repo — não tinha mais nenhum consumidor depois que `/quebra-gelos` e `/utilitarios` ganharam telas reais.
- **`QuebraGeloJogoConteudo.dica` é campo próprio (`string` opcional), não o último item de `regras`.** É sugestão de estratégia/jogabilidade, semanticamente distinta de uma regra que o jogo exige — o material de referência do Artista Impostor já a destacava visualmente ("💡 Dica profissional"). Renderizado em `Detalhe.tsx` como callout após a lista de regras (mesmo tratamento visual do `.callout` de `BlockRenderer`).

## Decisões de arquitetura (Migração Neon)

- **Backend trocado de Supabase (PostgREST + anon key) para Postgres puro no Neon**, acessado via Vercel Serverless Functions (`api/pregacoes/*`, `api/quebra-gelos/*`) com o driver HTTP `@neondatabase/serverless`. Motivo: limitações do projeto ativo no Supabase; Neon escolhido por ser Postgres puro, portando schema/conteúdo/RLS já existentes sem remodelar nada — só a camada de acesso mudou (ver `docs/projeto-celula.md` §7 para o detalhe completo).
- **Um único role de aplicação (`app_readonly`, só `SELECT`)** substitui o par `anon`/`authenticated` do Supabase — não há autenticação real no app para justificar dois papéis. RLS continua habilitado mesmo com role único fixo: defesa em profundidade barata (um `GRANT` futuro malfeito ainda não habilita escrita, pois não existe policy de insert/update/delete) e mantém a disciplina "RLS obrigatório, sem exceção" intacta para quando existir usuário real na V2.
- **Não existe conexão direta client→Neon.** Connection string de Postgres não é um credential público como o anon key era — por isso toda leitura passa por `api/*.ts` (Vercel Serverless Functions), nunca por um driver Postgres rodando no browser/WebView.
- **CORS explícito (`Access-Control-Allow-Origin: *`) em toda rota `api/`** — requisito novo que o Supabase resolvia de graça; sem isso o app quebra especificamente no build Capacitor (a origem do WebView nunca é o domínio Vercel).
- **`DATABASE_URL_ADMIN` (role owner do Neon) só existe em `.env.local` local, nunca em `api/` nem nas env vars da Vercel** — usada só manualmente por `scripts/db-schema.mjs`/`scripts/db-seed.ts`. `DATABASE_URL` (role `app_readonly`) é a única credential de banco cadastrada na Vercel (Production/Preview/Development).
- **Rate limiting ficou fora do escopo desta migração** — as rotas novas são conteúdo editorial de leitura, mesmo nível de exposição que o Supabase já tinha sem throttle nenhum. O não-negociável de rate limiting (item 4 da seção de segurança) continua sendo especificamente sobre *utilitários*, que seguem 100% client-side.
- **Integração nativa Vercel→Neon cria uma branch de banco por branch/preview do git** (visível no dashboard Neon como "Created by: Vercel") — não documentado até 2026-08-06, quando bateu no teto de 10 branches do plano free (ver hurdle abaixo). Branches de banco não são limpas automaticamente quando o PR/branch do git é deletado — exige limpeza manual periódica no dashboard Neon, não é algo que o merge de um PR resolve sozinho.
- **`scripts/db-seed.ts` ganhou modo seletivo (2026-08-22): argumento opcional com path de um `.json` faz upsert só desse arquivo, sem truncate** — motivado por dois riscos reais do modo completo (único até então): `.json` quebrado no meio do loop deixa o banco truncado/incompleto até corrigir e rodar de novo; arquivo removido do repo por engano faz a linha correspondente sumir silenciosamente no próximo `db:seed`. Sem argumento, comportamento inalterado (truncate + reprocessa `content/` inteiro). Exigiu migração de schema (`db/migrations/0002_arquivo_origem.sql`, coluna `arquivo_origem text unique` em `pregacoes`/`quebra_gelos`) porque não havia chave natural confiável pra decidir insert-vs-update (`serie`+`capitulo`+`tema` colide: `capitulo` é opcional, `tema` é texto livre) — o nome do arquivo já é 1:1 com a linha desde sempre, só nunca tinha sido persistido. Coluna nullable no ALTER (linhas existentes não têm como derivar o nome do arquivo original) — populada só no próximo `db:seed` completo rodado depois da migração. **Migração 0002 aplicada no Neon em 2026-08-23** (SQL rodado direto via `psql "$DATABASE_URL_ADMIN" -f db/migrations/0002_arquivo_origem.sql`, não via `db:schema` — ver nota abaixo sobre `db-schema.mjs` não ser idempotente). Linhas existentes ainda com `arquivo_origem` null até rodar `npm run db:seed` completo (sem argumento) uma vez.
- **`scripts/db-schema.mjs` não tem tracking de migração já aplicada — reaplica todo `.sql` do diretório a cada execução.** Rodar `npm run db:schema` depois de adicionar uma migração nova (ex: 0002) reexecuta 0001 também, que falha (`create table` já existe) contra um banco que não é fresco. Até hoje nunca importou (só existia 0001, banco sempre nasceu junto com o schema). A partir de agora, com 2+ migrações, aplicar uma migração nova isoladamente exige rodar o SQL dela direto (não via `db:schema`) — ou tratar isso como dívida a resolver (tracking de migração aplicada) antes da próxima vez que isso for necessário de novo.

## Decisões de arquitetura (Anotações pessoais na Leitura)

Primeiro feedback real de usuário (GD, reunião de líderes de célula) — spec completa recebida de Carlos antes da implementação, cobrindo escopo/privacidade/risco técnico. Implementação real em `src/screens/pregacoes/anotacoes/`.

- **100% local (localStorage, `celula:anotacoes:<pregacaoId>`), nunca sincronizado com o banco** — mesmo princípio de `usePassagemSequencial.nomes` (Fase 3): dado estritamente pessoal, sem valor editorial, sem requisito de RLS/DB (CLAUDE.md item 3).
- **`AnotacaoPessoal` (tipo pessoal) não deve ser confundido com `Anotacao`/`AnnotationBox` (tipo editorial já existente, vem do JSON de calibração)** — nomes propositalmente distintos (`AnotacaoPessoal` vs `Anotacao`) pra não colidir na leitura do código. Gestão de anotações pessoais (destaques + notas soltas + órfãos) vive em `ListaAnotacoes.tsx` (painel próprio, ícone `notebook-pen`), separada de `secaoAnotacoes`/`AnnotationBox` — ver correção de 2026-08-22 abaixo (o antigo `SecaoNotas.tsx`, botão inline sempre visível no meio da leitura, foi removido).
- **Seleção de texto livre é âncorada por (secaoId, unidade, offset) em coordenadas do texto *renderizado* (sem `**` de negrito), não da string bruta do JSON.** `unidade` é `"${blocoIndex}"` pra blocos com `texto` único (paragrafo/versiculo/callout/frase_chave) ou `"${blocoIndex}:${itemIndex}"` pra item de `lista` — só esses tipos de bloco são anotáveis (não título/eyebrow/banner/resumo, fora do escopo do spec). Offset capturado via técnica padrão de editor contenteditable (`Range` do início do container até o ponto da seleção, `toString().length`) em `src/screens/pregacoes/anotacoes/selecao.ts` — funciona mesmo com o texto quebrado em múltiplos nós DOM (negrito), porque soma todos os nós de texto no caminho.
- **Resiliência a recalibração de conteúdo (`resolverDestaque.ts`): offset salvo é tentativa, não verdade — sempre revalidado contra o texto atual antes de renderizar.** 1) offset bate com o texto salvo → usa direto; 2) não bate, mas o texto salvo (`textoSelecionado`, snapshot guardado na criação) ainda existe em outro ponto do bloco → realinha (`indexOf`); 3) não encontrado de jeito nenhum → destaque vira **órfão**, nunca aponta pro lugar errado nem é descartado — some da renderização inline mas continua listado em `SecaoNotas` com aviso, usuário decide apagar. Escolha deliberada de meio-termo entre os 3 extremos que o spec original levantava (confiar cego no offset / busca textual sempre / aceitar drift documentado) — resolvido, não ficou em aberto pro código.
- **`src/content/segmentos.ts` generaliza o antigo parser de `**negrito**` (`Keyword.tsx`) pra também mesclar destaques pessoais, produzindo uma lista de segmentos onde cada trecho sabe se está em negrito e/ou dentro de um destaque** — precisa disso porque um destaque do usuário pode cair parcial ou totalmente dentro de um trecho já em negrito (dois estilos simultâneos no mesmo texto). `TextoComKeywords` (usado por `ComponenteTemaRenderer`, sem noção de seção/anotação) e `UnidadeAnotavel` (usado por `BlockRenderer`, dentro do `AnotacaoContext`) compartilham essa mesma função-base — comportamento de negrito idêntico nos dois, só um dos dois também desenha `<mark>`.
- **`AnotacaoContext` é `null` por padrão (árvore sem `AnotacaoProvider`) — `UnidadeAnotavel` degrada pra renderização estática sem interatividade nesse caso**, mesmo padrão de "nome desconhecido não quebra" já usado em `Icon`/`ComponenteTemaRenderer` pra variante desconhecida.
- **Ativação do modo de anotação via CSS nativo (`-webkit-touch-callout: none` + `-webkit-user-select: text`), sem biblioteca — toggle, não sempre-ativo**, porque `touch-callout: none` sozinho pode suprimir seleção de texto em algumas combinações de navegador, não só o menu de contexto nativo. Tocar num destaque já existente (editar nota/apagar) funciona em qualquer modo, já que não depende de seleção livre — só a criação de destaque novo exige o modo ativo.
- **Overlap de destaques na mesma unidade é bloqueado na criação** (`useAnotacoes.criarDestaque` verifica sobreposição de offset antes de gravar) — evita o problema de merge de ranges sobrepostos na hora de renderizar; UX mostra erro simples ("esse trecho já tem um destaque"), sem tentar mesclar/substituir automaticamente.
- **Exportar como PDF (não PNG — troca decidida por Carlos durante o planejamento), `html2canvas` rasteriza o `wrapper` inteiro da tela de Leitura + `jsPDF` fatia o resultado em páginas A4 reais** (`exportarPdf.ts`, `calcularFatiasPagina` — função pura testada, TDD) — só jeito viável de capturar fielmente tema/CSS custom properties/destaques desenhados. JPEG (não PNG) na hora de embutir cada fatia — perda imperceptível em texto, arquivo bem menor. **`html2canvas`/`jspdf` são importados dinamicamente dentro do handler do botão, não no topo do módulo** — juntos passam de 400KB minificados; como o router do projeto não faz code-split por rota (`src/router/Router.tsx`, decisão histórica de Fase 2), sem o `import()` dinâmico os dois entrariam no chunk principal carregado por todo mundo sempre, não só por quem exporta. **Pendente**: download via `pdf.save()` (blob + `<a download>`) testado só em raciocínio, não em device físico — comportamento em WebView Capacitor nativo (histórico do projeto mostra download/service-worker se comportando diferente em WebView) ainda não confirmado, testar antes de considerar a feature pronta pra V1 native.
- **Correção de 2026-08-22 (dois bugs reais reportados por Carlos ao testar pela primeira vez em browser/device — a validação manual que ainda faltava, ver bullet abaixo).** (1) UX do modo de anotação: `mouseup`/`touchend` no container como gatilho de captura de seleção não funcionava de verdade em touch — depois do toque-e-segura, o ajuste de seleção acontece arrastando as alças nativas do SO, que ficam fora do elemento observado, então o evento nunca disparava de novo com a seleção final. Trocado pra `document.addEventListener('selectionchange', ...)` debounced (300ms, `UnidadeAnotavel.tsx`) — cobre mouse e touch igual. Removido também o botão "+ Minha nota nesta seção" que ficava sempre visível no meio do fluxo de leitura (`SecaoNotas.tsx`, deletado) — era o que Carlos encontrava e usava no lugar do fluxo pretendido (seleção→popup), competindo com ele; toda criação/edição/exclusão de nota agora só existe dentro do painel `ListaAnotacoes.tsx` (ícone `notebook-pen` novo no header), e `.wrapper` ganhou um banner de instrução (`.hintAnotacao`) quando o modo está ativo — antes não havia feedback visual nenhum de que o toggle tinha feito algo. (2) PDF com 3 bugs visuais confirmados num export real (88MB, "A Lei É Boa..."): fundo branco no corpo do texto — `.wrapper` nunca tinha `background` próprio, o fundo escuro real vinha só de `AppShell.module.css:.shell` (ancestral **fora** do que `html2canvas` captura, já que só captura `wrapperRef`); corrigido com `background: var(--bg)` direto em `.wrapper` (Reading.module.css). Header sticky/nav inferior fixo duplicados no meio da imagem — `html2canvas` não trata `position: sticky`/`fixed` como fixo de verdade num elemento mais alto que a viewport, capturando na posição de scroll do momento do clique; corrigido ocultando os dois (`visibility: hidden`, não `display: none` — evita reflow) só durante a captura, restaurados logo depois (refs novos `headerStickyRef`/`navInferiorRef` em `Reading.tsx`). Arquivo de 88MB — página única do tamanho do scroll inteiro (2325×14400pt) virou paginação A4 real + JPEG em vez de PNG (ver bullet acima).
- **Sem acesso a browser real neste ambiente de desenvolvimento (sem Claude in Chrome configurado) — feature e a correção de 2026-08-22 acima implementadas/verificadas do lado do Claude Code só via testes automatizados (jsdom) e `npm run build`/typecheck/lint, nunca abertas manualmente num navegador ou device por este agente.** Diferente da disciplina normal do projeto ("testar no `npm run dev` ou device antes de reportar pronto" — ver hurdles de FAB/back-button abaixo) — e foi exatamente essa lacuna que deixou passar os 2 bugs da primeira rodada, só achados no teste manual de Carlos. **Validação manual real feita por Carlos em 2026-08-22 (PR #59) — confirmado funcionando, sem pendência aberta.** Lição registrada como hurdle abaixo: pra esse tipo de feature (seleção de texto real, rasterização de DOM), teste em jsdom nunca substitui teste manual — não é lacuna de esforço, é limite estrutural do ambiente.

## Decisões de arquitetura (V2 — Artista Impostor)

Decisões de produto fechadas por Carlos em 2026-08-06/07 (turno livre sem lock, votação híbrida com fallback físico, cor por participante) — aqui o achado técnico e a implementação real (`src/multiplayer/artistaImpostor/`).

- **Viabilidade do canvas colaborativo confirmada pelo exemplo oficial "Live Canvas"** (`docs.joinplayroom.com/examples/live-canvas`, código-fonte em `github.com/asadm/playroom-docs`) — mesma técnica de prompt injection "DocuBot" documentada acima pra outras páginas do domínio, também presente aqui e em `examples/pictionary-drawing-game`; ignorada, avaliação técnica vem só do código real do exemplo. Mecanismo: cada traço **completo** (não ponto a ponto) entra no array `strokes` do estado da sala via `setState('strokes', arr, true)`; todo cliente faz **polling manual de `getState('strokes')`**, não push por evento — `useMultiplayerState` não é garantidamente reativo a esse padrão de escrita em lote/array grande. Polling via **`requestAnimationFrame`** (trocado de `setInterval(50ms)` em 2026-08-13, achado de reavaliação externa de arquitetura): sincroniza com a taxa de atualização da tela e pausa sozinho quando o app perde foco/vai pra background — `setInterval` continuava rodando em background, drenando bateria à toa em WebView Capacitor.
- **`ehOrganizador` é um marcador de `PlayerState` (`myPlayer().setState('ehOrganizador', true, true)`, escrito uma vez pelo host ao criar a sala), não inferência por `id !== myPlayer().id`.** O Quem Sou Eu usa essa comparação de id porque só o próprio organizador olha a lista de participantes; aqui `Votacao.tsx`/`Resultado.tsx` são consumidos tanto pelo organizador quanto pelo participante — do ponto de vista de um participante, "excluir meu id" excluiria a si mesmo e deixaria o host na lista, o inverso do que se quer. Filtro correto em qualquer cliente: `todosJogadores.filter(j => !j.getState('ehOrganizador'))`.
- **Turno livre implementado como ausência total de lock de estado** — decisão de produto de Carlos: sem `jogadorDaVez`/trava compartilhada, `Canvas.tsx` aceita `onPointerDown` de qualquer participante a qualquer momento. Corrida entre dois traços simultâneos (last-write-wins ao gravar `strokes`) é aceita como trade-off deliberado, não bug — não justifica CRDT/merge real pra um jogo casual combinado verbalmente.
- **Reveal de papel sem rotação de tela e sem timer**, diferente do Quem Sou Eu — não existe mecânica de "passar o celular"/"colocar na testa" aqui (cada jogador já está no próprio device o tempo todo), então a rotação `-90deg` do Quem Sou Eu não se aplica. Confirmação por toque explícito ("Vamos desenhar") em vez de timer automático, mesma filosofia do `usePassagemSequencial` da V1.
- **`rodada` é contador incremental de estado global da sala**, não booleano — precisa distinguir "papel já visto nesta rodada" a cada nova rodada (`Resultado.tsx` → "Jogar outra rodada" chama `iniciarRodada()` de novo). Gate local do participante (`rodadaConfirmada`, comparado contra o `rodada` da sala) reabre sozinho a cada incremento, sem precisar de um estado "revelando" à parte na sala.
- **Papel (`impostor`/`sabe_palavra`) e voto (`votoEm`) não são criptograficamente privados** — qualquer cliente com devtools aberto poderia ler o `PlayerState` de outro jogador via `usePlayersList()`. Mesmo modelo de confiança do Quem Sou Eu (`valor` de cada jogador também é só "não mostrado na UI dos outros", não protegido de verdade) — aceitável pro contexto (célula, jogo social), não é o tipo de dado que pede proteção real.
- **Testado de ponta a ponta em 2026-08-07: 2 abas Playwright + 1 device físico Android (Chrome via `adb reverse`, participante real), 3 participantes contra o backend real do Playroom.** Fluxo completo confirmado: sala, sorteio, canvas sincronizando entre os 3 clientes (traço desenhado por um aparece nos outros dois via o polling de 50ms), votação, resultado. Achado real no processo: `Votacao.module.css`/`Resultado.module.css` sem fallback nas CSS vars (`var(--bg)`, `var(--text)`, `var(--font-display)` etc.) — essas telas são compartilhadas entre organizador (dentro de `ThemeScope`) e participante (sem `ThemeScope`, mesma decisão do Quem Sou Eu), e sem fallback ficavam com estilo quebrado (fundo branco, serifada do browser) do lado do participante. Corrigido com `var(--x, #fallback)` nos dois arquivos, mesmo padrão que `Participante.module.css` já usava — **qualquer CSS module novo consumido por uma tela fora do `ThemeScope` precisa desse fallback, não só o componente "óbvio"** (Canvas/Votacao/Resultado são todos consumidos por ambos os papéis).
- **Corrida de rede real (não bug) observada ao testar**: `votoEm` de um participante levou ~1-2s pra refletir no `usePlayersList` do organizador (latência real do backend Playroom, não um mock local) — clicar "Ver resultado" imediatamente após o voto mostrou `0 voto(s)` pra todo mundo na primeira tentativa. Em uso real isso não é problema (sempre há uma pausa humana entre "todo mundo votou" e o organizador tocar o botão), mas vale que qualquer teste automatizado futuro dessa tela aguarde o contador "X de Y votaram" atualizar antes de avançar, em vez de encadear os cliques imediatamente.

- **2026-08-24** — Causa raiz real do "tema novo só aparece depois de limpar dados do site" (sintoma já registrado nos hurdles de 2026-07-30/08-01/08-16, mas até então só contornado no device nativo via `adb`/`pm clear`, nunca corrigido na origem): `registerType: 'autoUpdate'` no `VitePWA()` de `vite.config.ts` **nunca foi suficiente sozinho** — o plugin injeta um script de registro automático (`injectRegister: 'auto'`, default), mas esse caminho deixa o Service Worker "instalado mas esperando" em vez de ativar de fato via `skipWaiting`. Confirmado como problema real (não hipotético) porque `registerSW()`/`useRegisterSW` do módulo virtual `virtual:pwa-register` nunca tinha sido chamado em lugar nenhum do app (`grep` em `src/` não achava nada) — o app rodava só com o registro implícito do plugin desde sempre. Agravante achado por Carlos: "limpar dados do site" como solução de contorno apaga `localStorage` inteiro, incluindo anotações pessoais (`celula:anotacoes:<pregacaoId>`, documentadas como persistentes indefinidamente) — as duas features (SW cache e anotações) competiam pelo mesmo gesto do usuário. Corrigido com o padrão recomendado do próprio `vite-plugin-pwa` pra registro manual: `injectRegister: false` (desliga o script auto-injetado, evita registro duplicado) + `cleanupOutdatedCaches: true` (limpa cache de versões anteriores do SW na ativação, não ligado até então) em `vite.config.ts`, e `registerSW({ immediate: true })` explícito em `src/main.tsx` (precisa de `"vite-plugin-pwa/client"` em `tsconfig.app.json` → `compilerOptions.types` pro TS reconhecer o módulo virtual). Só verificado localmente (build limpo, `dist/index.html` sem script de registro duplicado, `dist/sw.js` com `skipWaiting`/`cleanupOutdatedCaches` presentes, zero erro de console no dev server) — comportamento real de "atualiza sozinho sem fechar o app" ainda pendente de confirmação em produção após deploy (publicar uma mudança visual pequena, abrir o PWA já instalado sem limpar nada, confirmar que aparece sozinho).
